## 0. Implementer's quickstart

See the rendered version at [handshake.ai/spec#s-quickstart](https://handshake.ai/spec#s-quickstart) for the complete three-step quickstart with code samples in Python, TypeScript, and Go.

In short:

1. **Install an SDK** — `pip install handshake-sdk`, `npm install @handshake/sdk`, or `go get github.com/handshake-ai-protocol/handshake-go`.
2. **Generate a deployer identity** — Ed25519 keypair, store in HSM/KMS, publish DID Document at `/.well-known/handshake/did.json`.
3. **Wrap an agent call** — issue a delegation, perform a handshake, receive a signed receipt.

### 5.1 — Resolution convention (informative excerpt)

The full §5 prose is rendered from the website source. One convention is reproduced here in full because it is the contract every SDK already implements and is the load-bearing rule for org-level identifiers:

> **`did:hsk:org:<host>` MUST resolve at `https://<host>/.well-known/handshake/did.json`.**
>
> The DID Document at that URL is fetched over HTTPS, parsed as JSON, and validated against [`schemas/v0.2.3/did-document.json`](../schemas/v0.2.3/did-document.json). The `id` field of the document MUST equal the requested `did:hsk:org:<host>` exactly (string equality, no `alsoKnownAs` chain following).
>
> Example: `did:hsk:org:handshake.ai` → `https://handshake.ai/.well-known/handshake/did.json`.
>
> Per-tenant identifiers (`did:hsk:user:<id>`, `did:hsk:agent:<id>`, `did:hsk:svc:<id>`) resolve via the operator's Registry; see §5.2.

## §22 — Registry HTTP surface (v0.2.3)

The reference Registry implementation exposes the following HTTP routes
under each operator's deployment (e.g. `https://registry.handshake.ai`).
Two routes are publicly resolvable; the third is admin-gated.

### §22.1 `GET /v1/dids/{did}` (public)

Resolves a DID to its currently-cached DID Document, the published
Ed25519 verification key (raw 32-byte public key, base64url, no
padding), and the role.

* **Path parameter** `did` — the full DID, URL-encoded. Exact-match
  lookup; no `alsoKnownAs` traversal.
* **Filters** (server-enforced):
  * `role IN {service, agent, user}` — the four-role reservation in
    §5 leaves room for future roles (e.g. `operator`) that are NOT
    yet exposed at the unauthenticated surface.
  * The owning tenant MUST NOT be soft-deleted.
* **Responses**:
  * `200` — `{ did, role, document, primary_ed25519_pubkey_b64u, doc_version }`
  * `404` — `{ "detail": { "code": "did_not_found", … } }`. The same
    404 is returned regardless of whether the DID was never
    registered, was registered to a soft-deleted tenant, or has a
    non-public role; the ambiguity is intentional.

This is the read twin of `POST /v1/admin/dids` and removes the prior
need for an admin bearer token to resolve a DID.

### §22.2 `GET /v1/revocations/published` (public)

Returns the Registry-signed envelope of every revocation whose
`published_at` is non-NULL, ordered by `revoked_at DESC`. Verifiers
fetch this periodically to invalidate cached delegation tokens or DID
keys signed by a now-revoked principal.

* **Response shape** — see [`../schemas/v0.2.3/revocations-published-feed.json`](../schemas/v0.2.3/revocations-published-feed.json).
* **Signature** — every response carries a `signature` block at the
  top level. The signature is computed over the JCS canonicalisation
  of the envelope *with the `signature` field removed*, signed under
  the Registry's identity key (the same key advertised at
  `/.well-known/handshake/did.json` as `keys-1`). Verifiers MUST
  verify the signature before trusting any field of the body, since
  the response is served unauthenticated and may traverse caches.
* **Cache-Control** — the Registry sets `Cache-Control: no-store`. The
  feed is the source of truth for revocation state; stale caches
  actively undermine its purpose.

### §22.3 `POST /v1/admin/revocations/publish` (admin-bearer)

Publishes a revocation. Idempotent on `(subject_did, key_id, tree_head_id)`.

* **Auth** — same model as the rest of `/v1/admin/*`:
  `Authorization: Bearer <HANDSHAKE_ADMIN_TOKEN>`.
* **Body**: `{ subject_did, key_id, reason, tree_head_id }`. The
  `tree_head_id` is the operator's anchor proof of the revocation;
  the Registry stores it but does not re-verify the anchor at this
  surface (anchor verification has its own route, §22.X).
* **Responses**:
  * `200` — `{ id, published_at }`. Re-posting the same triple
    returns the original `id` and `published_at` unchanged (no
    second row created, no `published_at` rewrite).
  * `404` — the `subject_did` is not registered with this Registry.
